# v2.13.8 / 路由器 v1.4.58：TLS 错误与日志来源

## 现场证据

截图含 11 月 14 日起的历史日志；实查客户端为 v1.4.57，11 月 15 日 16:30:58 升级后也出现过新的 curl 35 告警，因此不能只解释成旧日志残留。

同一台路由器随后连续五次正常验证证书访问面板均为 HTTP 200、ssl_verify_result=0。该结果证明这些请求当时的证书验证正常，不保证链路永不发生新的 TLS 握手失败。

## 根因与修复

- curl 35 是 TLS 握手失败，不能等同于对端证书验证失败。CLI、agent、性能模块与安装探测之前把一大组 TLS/本地配置错误都当成证书错误并允许跳过验证；现仅对 51/60 保留原有对端证书验证兼容路径。35、超时、本地 CA 配置、TLS 引擎和密钥固定等错误不会因此关闭验证。
- 无 curl 的 wget/uclient-fetch 分支不再仅因 stderr 含 SSL、TLS 或 certificate 就降级，而是要求明确的证书验证失败信息。
- agent 心跳对短暂握手错误保留验证重试。三次仍失败会记录真实的“TLS 握手失败 (curl 35)”；不通过压掉错误掩盖持续故障。
- perf.sh 的全局 log 函数覆盖了导入它的 agent 的同名函数，导致普通心跳/配置更新也标成 zeroproxy-perf。现性能模块使用 zp_perf_log，agent 保持 zeroproxy-agent。
- agent 大文件下载原先在失败的 if 语句之后获取退出码，可能错误得到 0。现直接保存 curl 的实际失败状态。
- 性能模块原先仅在 HTTP code 为空时处理证书错误，而真实 curl 经常输出 000；现按退出码判断，并保留重试响应头用于摘要校验。旧认证回退时的 URL 与请求头也保持一致，测试确认不将令牌写入进度输出。

- Python 最终全套：638 项通过、6 项跳过；JS/shell 语法和发布清单检查通过。
- Chromium：197/197 项通过；路由器安装模拟：201/201 项通过；服务器升级与失败回滚模拟及 Go 测试通过。
- 定向请求/日志回归：91 项通过，包含所有原先允许降级的 curl 错误码、严格重试恢复、持续握手失败、旧认证目标与响应头保留。
- 实际 OpenWrt BusyBox ash 中仅导入修复后的辅助函数，使用隔离替身验证：agent 与性能标签分别正确，第一次 curl 35 后第二次严格请求成功，未使用不校验请求。没有重启或修改正式运行服务。
