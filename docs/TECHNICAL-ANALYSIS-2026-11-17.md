# ZeroProxy 技术分析与升级建议

分析日期：2026-11-17（北京时间）。代码基线：`afd4cf6`，面板 v2.15.3，路由器客户端 v1.4.59。本文是分析交付，不修改业务代码或生产配置。

## 结论

ZeroProxy 已经从“代理节点安装面板”发展为一套小型网络运维系统：服务器负责生成配置和分发资源，路由器负责实际接管流量，网页负责操作与证据展示。

它的优势是部署自动化、老固件兼容、多协议、多服务器、离线自治和变更回滚。下一阶段最有价值的工作是把现有能力闭环做严：**用户意图必须准确传到运行现场，运行成功必须有证据，状态查询不能阻塞控制指令。** 此后再用同硬件、同线路的对照实验优化吞吐。

当前没有足够数据证明它已经达到同类项目的最高吞吐，也不能把任何上游项目客观排为“最强”。参考应按子问题选择，详见 [上游一手资料研究](UPSTREAM-REFERENCE-2026-11-17.md)。

## 1. 分析范围和证据等级

本轮检查 Python 后端、网页模块、路由器安装与运行脚本、Go 本地控制面、配置生成器、升级脚本和现有回归入口。沿入口、状态写入、配置生成、内核应用、回报、前端呈现逐段追踪主要功能。

- **已复现**：在隔离临时目录运行实际函数或摘取的原始脚本片段，外部系统命令使用替身。
- **源码确认**：控制流直接支持结论，但未在真实 Linux/OpenWrt 上重现对应故障。
- **待测建议**：技术上有优化机会，收益必须实测，不能当成已测瓶颈。

回归通过说明已覆盖的场景通过，不表示所有分支都正确；本轮新增复现正好揭示现有测试之外的缺口。没有连接、升级或压测生产服务器和真实路由器。

## 2. 系统如何工作

```text
网页：登录／配置／任务进度／限时确认／诊断证据
  ↓ HTTPS，nginx 反向代理
FastAPI：鉴权、参数校验、配置版本、后台任务
  ↓
state.json：期望配置＋会话＋设备状态＋审计
  ↓ 配置生成、真实内核校验、按变化重启或重载
Xray / Hysteria 2 / WireGuard：服务器实际转发

路由器：配对 → 获取 mihomo／dae 与规则资源 → 探测接管方式
  → 应用配置 → 接管 LAN／本机流量 → 心跳报告实际状态
  → 网页展示在线、运行、接管范围、配置版本和诊断结果
```

**用户的数据流量主要经过代理内核，不经过 Python 面板。** 因此降低面板响应时间能改善操作和同步，但不会直接等比例提高下载速度。转发性能应看路由器 CPU、数据面、协议、服务器出口、丢包、DNS 与 MTU。

## 3. 交互与功能逻辑地图

| 功能链路 | 已有实现与价值 | 当前边界／下一步 |
|---|---|---|
| 初始化、登录、域名交接 | 引导令牌、会话、限流、证书申请、跨域名一次性交接；前端处理密码显隐、重复提交和断线 | 证书失败与自签回退必须继续显式展示；不要将开发模式结果当线上可用证据 |
| 节点与高级参数 | 参数与端口冲突校验，内容版本校验；统一生成 Xray/nginx/Hysteria 配置 | 配置变化仍可能重启内核并中断连接；应区分支持动态操作的变更与必须重启的变更 |
| 配置应用与恢复 | 后台任务、步骤记录、持久化、最近成功配置、失败文件恢复、监听端口验证 | 写盘与运行应用不是同一事务；服务端监听成功也不能证明远端或 LAN 能出网 |
| 限时网络变更 | 网页申请保护、成功后开始 90 秒倒计时、后台回滚、重启后恢复检查、漂移保护 | 旧 API 未申请确认仍走兼容路径；系统进程完全停机期间看门狗不能执行，需恢复后处理 |
| 分享和订阅 | Base64、mihomo YAML、sing-box JSON；链接稳定，配置内容随状态变化 | 跨内核配置语法与功能语义须分别验收；某格式能被解析不代表真实协议全部可用 |
| 分流、广告和 DNS | 有序规则、自定义冲突分析、国内显式域名兜底、Geo 缺失降级、fake-IP 与节点域名引导解析 | 规则预估不能模拟实际 DNS、Geo、手动选组；发现全局模板到路由器的传递缺口，见 F2 |
| 链式代理 | 独立落地凭据、配对、TCP/QUIC 内层、证书指纹、默认出口和路线探测 | QUIC 部分异常为局部告警，不一定令整次应用失败；要保留“面板可用但某条链路失败”的区别 |
| 路由器安装 | 面板分发资源，多镜像与摘要，TUN→TPROXY→REDIRECT→无接管的实探测降级 | REDIRECT 仅 LAN TCP；不具备 IPv6 接管能力时继续提示；真实固件矩阵仍必要 |
| 路由器远程／本机控制 | 期望与实际状态分开；本机覆盖、离线保持；Go 本地控制面适配不同 Web 宿主 | 发现本机开启覆盖优先级和运行应用确认缺口，见 F1/F3 |
| 多面板聚合 | 独立设备凭据、proxy-providers、节点前缀、健康检查 | 版本目前取首个应答面板，后续面板变更不能可靠触发即时刷新，见 F5 |
| WireGuard / AWG | 独立 peer、到期回收、一次性链接、`syncconf` 增量同步、事务锁与失败补偿 | WG/AWG 切换可能重建接口；混淆模式不应承诺标准 WG 兼容；真实 AWG/IPv6 流量需另验 |
| 诊断与流量 | 浅探测、临时真实客户端深探测、设备请求与回报 ID、有效期、流量缓存与审计 | `healthy` 仍有仅代表进程在的路径；服务端、设备端、LAN、特定站点的证据必须分开 |
| 备份、恢复、升级、卸载 | 原子文件、加密备份、校验、systemd 托管升级、回滚与还原快照 | 摘要校验和发布身份认证是不同问题；恢复、版本迁移、在线升级需要持续故障注入验收 |
| 网页工作区 | 五工作区、搜索、草稿和焦点保护、任务恢复、可见的错误与证据时间 | 后台仍拉取整份仪表盘、重绘隐藏工作区；自适应轮询也会拉长外部变化的显示延迟 |

主要定位：`backend/zeroproxy/routes.py`、`apply.py`、`config.py`、`change_guard.py`、`share_links.py`、`devices.py`、`wireguard.py`、`chain*.py`、`client/runtime/`、`client/agent/`、`backend/static/app/`。

## 4. 应优先修正的具体问题

### F1：路由器重启失败仍返回配置应用成功（高优先级，已复现）

- 位置：`client/runtime/agent.sh:530–538`、`872–884`。
- 新配置通过语法校验并替换文件后，重启使用 `restart ... || true`，随后固定输出“配置已更新并重载”并返回 0。
- 主循环据此推进 `APPLIED_REV`。即使服务没有成功启动，后续心跳仍可能携带新的已应用版本。关闭状态下也会把仅落盘配置推进到已应用，说明版本语义还不够严格。
- 隔离复现将重启替身设为退出 42，实际函数仍输出成功，返回 0。
- 建议：分开 `downloaded / validated / staged / running / verified`；运行模式应验证控制 API 就绪、运行配置版本、数据面和固定目标后推进运行版本。失败保留旧运行版本并恢复旧配置。关闭状态仅标记 staged，不启动服务。

### F2：“跟随面板”模板被请求中的 smart 覆盖（高优先级，已复现）

- 位置：`client/runtime/agent.sh:176/179`；`routes.py:client_subscription`；`share_links.py:template_of`。
- agent 单服务器和多服务器骨架请求均写死 `rules=smart`。服务端优先使用设备独立模板，否则采用请求的 rules；因此设备模板为空时，smart 覆盖面板保存的 global/direct/precision。
- 用实际 `client_subscription` 选择路径复现：面板模板 global、设备模板为空、agent 参数 smart，渲染器实际收到 smart。复现替换了配置序列化，未替换模板选择逻辑。
- 建议：跟随模式省略 rules；明确优先级“设备覆盖 → 显式临时请求 → 面板全局 → 默认”。以生成的真实配置验证四种全局模板，而非只校验界面标签。

### F3：本机强制开启会被面板关闭覆盖（高优先级，已复现）

- 位置：`client/runtime/agent.sh:724–737`、`793–795`。
- 本机 override=on 先把聚合期望设为 true，后续任一面板 desired=false 又将它改回 false；源码注释承诺的“本机覆盖优先”在开启方向不成立。override=off 的当前优先级则能保留。
- 原始 shell 分支隔离执行结果：override=on＋panel=false → 最终 false。
- 建议：先汇总面板状态，再最后应用本机 override；明确展示谁在控制、为何关闭。补“本机开/关 × 单/多面板 × 面板在线/离线”的状态矩阵。

### F4：仪表盘的慢采集持有全局配置锁（高收益性能项，已复现结构）

- 位置：`routes.py:1339–1348`、`_dashboard_body`、`_system_view`；`services.py:xray_stats`。
- 仪表盘在 `config.locked()` 内调用完整构建；里面可能执行 Xray stats 命令、多个 systemctl 查询、WireGuard 状态及资源目录检查。Xray stats 命令本身允许 20 秒超时。
- 隔离实验仅给仪表盘构建注入 300ms 等待，同时尝试取得配置写锁，实际等待约 301–305ms。它证明锁耦合，**不是线上接口延迟测量**。
- 建议：锁内只鉴权、复制状态和必要清理；锁外收集系统信息。独立采集器缓存 1–5 秒，记录采样时间和失败原因，合并同一时刻的重复采集。返回配置版本以避免将旧快照当新证据。
- 预期改善：心跳、开关和登录的尾延迟；不直接提升代理吞吐。

### F5：多面板共用一个已应用版本（高优先级同步项，源码确认）

- 位置：`client/runtime/agent.sh:120`、`769–773`、`797`、`872–884`。
- 每轮从首个成功应答面板取得 REV；所有面板收到相同 LAST_REV/APPLIED_REV。但不同面板配置哈希本来不同。
- 后续面板变更不会改变首个面板的 REV，不能触发这一轮完整配置刷新；provider 自身还有 3600 秒刷新路径，完整配置另有 6 小时兜底，不能把它写成“永远不刷新”。
- 后续面板也可能因收到另一面板的 applied_rev 而持续显示版本不一致。
- 建议：保存 `{panel_id: desired_rev, downloaded_rev, staged_rev, applied_rev}`；聚合版本由排序后的面板版本向量生成。刷新对应 provider，并逐面板报告自己的版本。用两台模拟面板分别改节点、凭据、模板、断线恢复验收。

## 5. 性能优化：按实际收益排序

### 5.1 先改善操作响应与同步

1. **缩短锁范围与复用观测数据**：优先实施 F4，比重写后端语言更直接。
2. **减少无效任务轮询**：当前任务最初 2 秒每 100ms、随后每 400ms 请求。可先退避至 250ms→1s→2s，或使用可重连 SSE；无论哪种都保留持久化任务 ID 和最终状态查询。
3. **按工作区加载与更新**：设备、WG、资源、审计、系统遥测分开；仅重绘当前可见区域，维护页按需取资源信息。当前 `renderDash` 会调用几乎所有区域渲染器。
4. **避免并行旧请求覆盖新状态**：用完成后 setTimeout 或 single-flight 替代无约束 setInterval；操作后递增请求代数，丢弃旧响应；后台标签页降低采样频率。
5. **区分配置版本和观测版本**：当前 dashboard fingerprint 不含实际服务和设备状态，尽管注释提到服务状态。静默期可到 60 秒，外部故障发现会延迟。配置 ETag 与遥测 observed_at 分开，保持轻量健康采样。
6. **控制写盘范围**：会话、设备心跳、配置、任务目前分散为 JSON 状态和任务文件。先测 fsync 和锁等待，批处理遥测、缩小配置哈希影响范围；一台设备模板变化无需让其他设备重建。只有规模和测量支持时再迁移 SQLite WAL，不必先上 Redis/PostgreSQL。

### 5.2 再降低配置变更造成的断流

已有“配置摘要不变就不重启”和 WireGuard `syncconf`，应保留。

- 建立变更计划：客户端列表、规则、监听端口、传输参数分别影响哪些内核；只处理受影响部分。
- mihomo 优先研究外部控制器支持的重载和 provider 更新；Xray 优先验证对应 API 对用户／入站等变更的支持范围。必须明确哪些操作仍需重启，不能笼统承诺无损热更新。
- 在独立候选目录生成并校验完整配置集合，再提交。现状虽然有原子单文件和失败恢复，仍是逐个改写活动配置，原子单文件不等于多服务事务。
- 把“配置通过”“进程就绪”“监听就绪”“协议通过”“LAN 出网通过”作为不同证据；热重载也要测旧连接保留、新连接可用及失败回退。

### 5.3 真正提升网络转发性能

| 候选方向 | 适用条件与方法 | 不能预先承诺的事 |
|---|---|---|
| 升级 mihomo | 当前固定 v1.19.32；核验新稳定版的 TUN/路由修复，更新摘要和兼容矩阵后小范围验证 | 版本更新不等于吞吐一定增加 |
| TUN 与 dae 对照 | 当前已经是 `stack: system`＋auto-redirect；测同路由器同协议的 CPU、吞吐、首包、丢包、内存 | 无需重复“从 gVisor 改 system”；dae 缺 XHTTP，且目前策略组语义不等价 |
| MRS／分片规则资源 | 在 mihomo 支持的匹配类型中使用 MRS rule-provider，按策略实际需要加载，测冷启动和常驻内存 | 完整 GeoSite/GeoIP 不可机械替换，DNS 与其他内核仍依赖各自数据格式 |
| DNS 与 fake-IP | 分开测冷／热 DNS、域名首次连接、DNS 缓存命中、落地端解析；继续保证节点域名引导不形成环路 | 单一 DNS 上游或强制 DoH 不会对所有线路都更快 |
| MTU／UDP／拥塞 | PPPoE、WG/QUIC 封装分别测 PMTU；Hysteria 用丢包与速率曲线选择拥塞和带宽设置，观察 socket 丢包 | 不能把 WAN MTU 直接等同所有隧道最佳 MTU，不能任意调大缓冲或宣称 BBR 普适最优 |
| 认证开销 | 当前独立 Hysteria 认证启动 Python 并读 auth.json；在大量新连接场景测启动次数、认证 p95 和 CPU，必要时改独立常驻认证服务 | 家用 32 台上限下未证明它已是瓶颈；认证服务应保持面板离线可用 |
| 选路与故障切换 | 在延迟之外考虑连续成功率、抖动、有限吞吐样本，加入切换滞后和冷却 | 不宜每次短延迟变化都换出口；频繁换 IP 会损害会话稳定性 |

dae 不是全功能升级替代品：当前明确排除 XHTTP、使用统一代理组，并阻断 UDP/443 促使客户端回落；这些行为变化需要同吞吐结果一起呈现。

## 6. 推荐实施顺序与验收门槛

以下是工程目标，**不是已经达到的性能数字**。

| 阶段 | 工作包 | 完成标准 |
|---|---|---|
| A：正确性 | F1/F2/F3/F5、统一版本与状态语义 | 重启失败不能推进 running/applied；四模板一致；覆盖优先级矩阵通过；第二面板单独变更可同步 |
| B：控制面性能 | F4、采集缓存、任务退避、当前工作区增量渲染 | 注入 2 秒采集故障时，心跳／写配置不被该 I/O 锁住；同机压测心跳 p95 初始目标 <200ms；实际达标需测 |
| C：内核与资源 | mihomo 新稳定版、MRS 试点、动态变更计划 | 真实协议矩阵通过；新连接可用，原连接断流次数和最长中断时间有记录；内存和冷启动有对照 |
| D：数据面择优 | TUN/TPROXY/dae、DNS/MTU/QUIC 参数 | 同线路 3–5 次重复，记录中位数与 p95；吞吐收益不能以错误分流、IPv6 绕行或功能缩水换取 |
| E：发布与长期验证 | CI、签名发布、故障注入、长稳 | Linux/OpenWrt 真机矩阵；磁盘满、掉电、fw4 reload、上游失败、重启中断；至少 24–72 小时初步长稳观察 |

测试矩阵至少包含：TCP/UDP、IPv4/IPv6、智能/精细/全局/直连、五协议、标准/性能模式、单/双面板、关闭/开启、本机覆盖、订阅升级、凭据吊销、断网恢复。

网络基准应比较“同一设备直接运行同一代理内核”和“由 ZeroProxy 管理该内核”，再比较不同数据面。记录原始日志、版本、规则数据版本、CPU 温度／频率、出口、RTT、丢包、并发数、CPU/RSS、DNS、首次响应、持续吞吐和 p95。先定基线再承诺提升比例。

## 7. 本轮验证结果与限制

- 后端全套：`714 passed, 7 skipped`，131.32 秒。7 项默认未提供真实内核，不计入真实内核通过。
- 随后真实内核专项：`scripts/real_kernel_check.py` → `8 passed`，5.16 秒；使用本机缓存 Xray v26.11.9 与 Hysteria app/v2.14.0。它覆盖前述可选真实内核路径及策略验证，不是整套后端重新带内核执行。
- Go：`go test ./...` 通过。

## 8. 架构取舍

继续采用轻量 Python 控制面、成熟代理内核与渐进式 Go 路由器管理是合理方向。当前不需要整体重写为 Go/Rust、增加多 worker 或引入微服务。多 worker 会复制内存任务表、后台看门狗和进程内锁，反而要先解决领导者与跨进程任务协调。

可逐步把 `routes.py` 按认证、配置任务、设备、链路、WG 和维护拆分，但应首先提取稳定的业务接口及状态契约。收益来自减少行为漂移、缩短锁范围、降低重复系统调用和断流，而不是文件拆得更碎。

产品层面应统一显示五件事：**想要什么、已下发什么、正在运行什么、谁在控制、最近一次验证证明了什么。** 这能同时提升可靠性、可理解性和故障排查速度。
